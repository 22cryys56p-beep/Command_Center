The contract tells us those fields are required for those statuses. It is therefore reasonable for the Dashboard specification to expose them. But the *presentation details* remain open.

### `blockers` deserves special treatment

For `planned` and `current`:

* `undefined` is invalid.
* `null` is valid and means **no blockers**.
* `string[]` means blockers exist.

Therefore the Dashboard should have an explicit rendering rule:

> **A valid `blockers: null` value must render as an intentional “no blockers” state, not as missing or invalid data.**

That is a real behavioral requirement, not merely cosmetic preference.

### What we should NOT specify yet

We should **not** decide yet:

* cards vs. rows;
* badges vs. plain text;
* colors;
* exact typography;
* whether `progress` is a badge, bar, or label;
* whether `last_updated` is formatted or shown as ISO;
* whether `repo_reference` is a button/link;
* whether completed projects get historical information;
* whether the Dashboard has a “Back” button;
* whether it has actions beyond navigation.

Those belong in the next layer of specification, after we establish the Dashboard's **behavioral contract**.

### One more important observation

The current `ProjectRecord` contract deliberately makes `progress` a controlled vocabulary:

`not_started | underway | nearly_done`

That means Phase 4 should **not reinterpret progress as an arbitrary percentage**.

Likewise, `status` is a closed enum. The Dashboard should not invent additional statuses such as “blocked,” “paused,” or “in review.”

If such states are ever needed, that's a **data-model/architecture decision**, not a UI embellishment.

---

### Step 3C result

We can now state the core Dashboard content contract:

> **The Dashboard presents the active ProjectRecord's current state. It presents the common project identity information for every valid status and presents the additional metadata applicable to that status according to the ProjectRecord's tiered requirements. It does not invent fields, statuses, or interpretations not present in the ProjectRecord contract.**

That's solid enough to carry forward.

**Next: Step 3D — determine the Dashboard's behavior when the navigation state or ProjectRecord is invalid/missing.**

- - - - - 

### Step 3D — Invalid / missing state behavior

This is the point where the project's **“honest failure over silent degradation”** principle becomes concrete.

We have enough evidence to establish several things, but we need to distinguish what the existing code **requires** from what Phase 4 still needs to decide.

#### 1. No current project

`NavigationController` explicitly allows:

```text
object: null
depth: "category"
```

That is a **valid, expected state**.

So the Dashboard must not treat `object === null` as corrupted data.

It simply means there is no selected project to display.

The existing architecture therefore establishes:

> **No selected project is a legitimate navigation state, not an error condition.**

What remains open is what the Dashboard does visually in that situation.

---

#### 2. Navigation says “dashboard,” but the object isn't a project

`selectProject()` deliberately guarantees that a dashboard state contains:

```text
{
    kind: "project",
    project_id: ...,
    category: ...
}
```

And `goUp()` contains explicit guards against impossible state combinations.

That gives us a useful Phase 4 invariant:

> **A Dashboard render is expected to receive a navigation object of `kind: "project"`.**

If it doesn't, we should **not silently manufacture a screen or pretend everything is fine**.

The precise UI response remains an open decision, but the architectural requirement is clear:

> **Invalid navigation state must be handled explicitly rather than silently degraded into a plausible-looking Dashboard.**

---

#### 3. Navigation project exists, but the corresponding record doesn't

This is more interesting.

`NavigationController` stores a `project_id`.

`ProjectListView` obtains actual `ProjectRecord`s through the provider.

There is currently **no code in the supplied files establishing what happens if the controller has a project ID for which the provider returns no matching record**.

So this is genuinely an unresolved Phase 4 requirement.

Possible behaviors include:

* explicit invalid/missing-project state;
* diagnostic error;
* user-facing “project unavailable” state;
* some other deliberately specified failure mode.

**We should not choose one yet.**

What we *can* freeze is the principle:

> **A missing ProjectRecord must not silently become an empty or fabricated Dashboard.**

---

#### 4. Invalid ProjectRecord

`validateProjectRecord()` establishes deterministic validation.

It returns **all discovered issues**, rather than stopping at the first one.

That means the Dashboard cannot reasonably assume that every record supplied by the provider is valid.

But again, the current files don't establish whether Dashboard rendering itself is responsible for validation.

That is an important boundary question.

My recommendation is:

> **Phase 4 should consume the ProjectRecord contract and render according to its validity, but should not duplicate the data-layer validation algorithm.**

The validation function already owns that concern.

If Phase 4 needs to know whether a record is valid, it should use the established validation contract rather than reproduce the rules.

---

### Step 3D matrix

| Condition                               | Established requirement             | UI behavior                                       |
| --------------------------------------- | ----------------------------------- | ------------------------------------------------- |
| No selected project (`object === null`) | Valid state                         | **Open**                                          |
| Dashboard depth + category object       | Invalid combination                 | Must fail explicitly; exact presentation **Open** |
| Dashboard depth + project object        | Valid expected state                | Dashboard renders                                 |
| Project ID has no matching record       | Must not silently fabricate/degrade | Exact behavior **Open**                           |
| ProjectRecord fails validation          | Validation belongs to data layer    | Exact Dashboard presentation **Open**             |
| Valid ProjectRecord                     | Dashboard can render it             | **Established**                                   |

### The important boundary

We're now establishing a useful separation:

**NavigationController answers:**

> *Which project is selected?*

**ProjectRecordProvider answers:**

> *What is the project's data?*

**ProjectRecord validation answers:**

> *Is that data structurally valid?*

**Dashboard answers:**

> *How should the selected project's valid state be presented?*

That separation is consistent with the Flag #1 decision we just froze as **Option B**. The Dashboard should not turn `NavigationController` into a record gateway.

---

### Step 3D result

The strongest requirement we can add to the Phase 4 matrix is:

> **Phase 4 must define explicit behavior for every state in which a Dashboard cannot obtain a valid ProjectRecord. It must not silently substitute fabricated, stale, empty, or otherwise misleading project content.**

That gives us the architectural guardrail without prematurely choosing the UI.

**Next: Step 3E — identify the Dashboard's interaction responsibilities and, importantly, what it is *not* allowed to own.**

### Step 3E — Dashboard interaction responsibilities

We can now separate **Dashboard behavior** from **Dashboard rendering**.

The existing code gives us one very clear interaction pattern: `ProjectListView` does not manipulate navigation state directly. It calls:

```text
id="4k7j82"
this.controller.selectProject(project.project_id);
```

The controller remains the owner of navigation-state transitions.

The Dashboard should follow that same boundary.

### Established Dashboard responsibilities

The Dashboard will need to:

1. **Read the current navigation state.**
2. **Identify the active `project_id`.**
3. **Obtain ProjectRecords through the shared `ProjectRecordProvider`.**
4. **Locate the active ProjectRecord.**
5. **Render the project's applicable information.**
6. **Initiate navigation actions through `NavigationController` rather than modifying navigation state itself.**

The last point is particularly important.

The Dashboard should not do something like:

```text
controller.state = ...
```

or gain knowledge of how navigation destinations are constructed.

Its relationship is:

```text
Dashboard
   │
   ├── reads ────────→ NavigationController
   │
   ├── reads ────────→ ProjectRecordProvider
   │
   └── requests ─────→ NavigationController actions
```

### What Dashboard does NOT own

The architecture establishes several negative requirements:

| Concern                                     | Dashboard ownership |
| ------------------------------------------- | ------------------- |
| Navigation state                            | **No**              |
| Resolver calls                              | **No**              |
| ProjectRecord storage                       | **No**              |
| ProjectRecord validation rules              | **No**              |
| Provider construction                       | **No**              |
| Navigation transition mechanics             | **No**              |
| Project presentation                        | **Yes**             |
| User interaction with the displayed project | **Yes**             |

That keeps the Dashboard from becoming another controller.

---

## What about editing ProjectRecords?

This is where we need to stop and mark an open decision.

Nothing in the four supplied files establishes Dashboard editing behavior.

The `ProjectRecord` module is currently explicitly described as:

> “The record shape and its validation rules only.”

It does **not** read or write files.

So Phase 4 should **not silently assume that the Dashboard edits project records**.

At this point:

> **Dashboard is a presentation/interaction consumer of ProjectRecord data, not yet an editor of ProjectRecord data.**

If editing is intended, that needs an explicit architectural/data-layer decision before we implement it.

That is especially important because otherwise we'd be inventing a write path that the current architecture deliberately doesn't contain.

---

## What about navigation controls?

The Dashboard will presumably coexist with the orientation/navigation element.

But we already have an explicit boundary from WP12:

`NavigationController` owns resolver calls and navigation state.

Therefore, if the Dashboard needs to trigger:

* Up
* Top
* Previous
* Next

those actions should go **through the controller's public action methods**.

The Dashboard must not call:

* `resolvePaging()`
* `resolveUp()`
* `resolveTop()`

directly.

That's already an established rule from `NavigationController` and its `getAvailability()` contract.

---

## Resulting interaction contract

We can now write this into the requirements matrix:

| Requirement                                              | Status                                   |
| -------------------------------------------------------- | ---------------------------------------- |
| Dashboard reads navigation state                         | **Established**                          |
| Dashboard gets active `project_id` from navigation state | **Established**                          |
| Dashboard obtains records through shared provider        | **Established / ACP-frozen**             |
| Dashboard correlates ID → record                         | **Established architectural pattern**    |
| Dashboard renders ProjectRecord                          | **Established**                          |
| Dashboard owns navigation state                          | **Prohibited**                           |
| Dashboard calls navigation resolvers directly            | **Prohibited**                           |
| Dashboard constructs the provider                        | **Prohibited**                           |
| Dashboard duplicates ProjectRecord validation logic      | **Prohibited**                           |
| Dashboard edits ProjectRecords                           | **Open decision**                        |
| Dashboard creates/deletes projects                       | **Open / currently unsupported**         |
| Exact Dashboard navigation controls                      | **Open presentation/interaction detail** |

### Step 3E conclusion

The Dashboard is shaping up as a **consumer**, not a new domain authority:

> **NavigationController owns navigation. ProjectRecordProvider owns access to project data. The Dashboard consumes both contracts and presents the resulting project state. It does not become a second navigation controller or a project-data service.**

That is a very clean boundary.

**Next: Step 3F — determine the Dashboard's lifecycle and render coordination with `CommandCenterView`.**

## Step 3F — Dashboard lifecycle and render coordination

This is where the supplied `NavigationInspector` and `ProjectListView` code becomes especially useful.

### 1. `CommandCenterView` is the composition root

From the architecture we've already established, `CommandCenterView` owns the lifecycle of the Command Center components.

That means the Dashboard should **not construct its own controller or provider**.

The intended dependency direction is:

```text id="6o4j9f"
CommandCenterView
       │
       ├── NavigationController
       │
       ├── ProjectRecordProvider
       │
       ├── NavigationInspector
       │
       ├── ProjectListView
       │
       └── Dashboard
```

The important part is that the **same provider instance** is injected into every component that needs project records.

That's our frozen Flag #1 decision.

---

### 2. The Dashboard should be constructed once

`NavigationInspector` explicitly establishes a passive-view model:

> a caller must invoke `render()`.

`ProjectListView` similarly has a `render()` method rather than owning its own application lifecycle.

That strongly suggests the Dashboard should follow the same model:

```text id="2clz7v"
constructor(...)
render()
```

rather than:

```text id="w4u2px"
constructor(...)
startWatchingEverything()
subscribeToController()
subscribeToProvider()
renderWheneverSomethingChanges()
```

The latter would create another state-management mechanism.

We have no evidence that such a mechanism is wanted.

---

## 3. Who calls `render()`?

The answer should be **`CommandCenterView`**.

This is already explicitly established for `NavigationInspector`:

> “Re-render coordination (who calls render() and when) remains entirely deferred to Slice 7's CommandCenterView.”

And `ProjectListView` already follows the same general model.

So Phase 4 should preserve this architectural rule:

> **Child views render when instructed by the composition root; they do not independently coordinate application-wide rendering.**

That gives us:

```text id="t3gk4d"
User action
    ↓
Child / NavigationController action
    ↓
Navigation state changes
    ↓
CommandCenterView coordinates render()
    ↓
Dashboard.render()
ProjectListView.render()
NavigationInspector.render()
...
```

The exact list of components rendered at each state transition is still a later implementation detail.

---

## 4. Should Dashboard subscribe to navigation changes?

**No.**

Nothing in the current architecture establishes child-view subscriptions.

In fact, `NavigationInspector` explicitly **MUST NOT subscribe to state changes**.

That is strong evidence that state-change coordination belongs above the individual views.

The Dashboard should therefore not acquire its own subscription mechanism simply because it needs to respond to navigation changes.

Instead:

```text id="xj73up"
NavigationController
        ↓
CommandCenterView
        ↓
Dashboard.render()
```

---

## 5. Should Dashboard hide/show itself?

This is slightly less certain.

`ProjectListView` currently does:

```text id="a6m2t7"
if (state.depth !== "list") {
    this.container.empty();
    this.container.style.display = "none";
    return;
}
```

So there is an existing precedent for a view being responsible for its own visibility based on navigation state.

The Dashboard may reasonably do the same.

However, we should distinguish:

**Established pattern:**

> A view may determine whether it has content to render based on navigation state.

**Not yet established:**

> The exact DOM visibility strategy for the Dashboard.

So we shouldn't freeze `display: none`, `flex`, specific containers, etc. in the requirements document.

---

## 6. Dashboard lifecycle

The clean model is:

### Construction

`CommandCenterView` creates the Dashboard and injects:

* its container
* the `NavigationController`
* the shared `ProjectRecordProvider`

### Runtime

`CommandCenterView` calls `Dashboard.render()` whenever the application state requires the Dashboard to be refreshed.

### Destruction

`CommandCenterView.onClose()` owns teardown.

The Dashboard itself should not own application lifetime.

---

## Step 3F conclusion

We now have a fairly strong lifecycle contract:

> **The Dashboard is a composition-root-owned child view. It receives the shared navigation and record-provider dependencies through constructor injection, exposes a passive `render()` operation, and does not independently subscribe to or coordinate application state changes. `CommandCenterView` remains responsible for deciding when the Dashboard renders and for the Dashboard's lifetime.**

And this gives us an important architectural symmetry:

```text

        │
        │ state
        ▼
CommandCenterView  ← composition/lifecycle authority
        │
        ├──→ ProjectListView.render()
        ├──→ Dashboard.render()
        └──→ NavigationInspector.render()

ProjectRecordProvider
        │
        ├──→ ProjectListView
        └──→ Dashboard
```

That is consistent with **both** flags we've just resolved.

**Step 3F is therefore complete.**

## Step 3G — Consolidation: Phase 4 Dashboard Behavioral Contract

This is the point where we stop accumulating individual observations and turn them into one coherent Phase 4 contract.

The key distinction remains:

**Established requirements are not the same thing as UI choices.**

We should freeze the former and leave the latter open until they are actually needed.

---

### A. Dashboard purpose

The Dashboard is the **project-state presentation view** reached after a project is selected from `ProjectListView`.

Its responsibility is to present the selected `ProjectRecord`.

It is **not**:

* a navigation controller;
* a project-data service;
* a record repository;
* a validation engine;
* an application lifecycle manager.

---

### B. Dependencies and ownership

The Dashboard receives its dependencies from `CommandCenterView` through constructor injection.

Required dependencies:

* Dashboard container;
* `NavigationController`;
* the **same `ProjectRecordProvider` instance** used elsewhere.

This incorporates the finalized Flag #1 decision.

**Frozen boundary:**

> `NavigationController` is not a ProjectRecord gateway. Components that need ProjectRecord access receive the shared provider directly from the composition root.

The Dashboard must not construct either dependency itself.

---

### C. Navigation relationship

The Dashboard reads the controller's state to determine the active project.

Expected Dashboard state:

```text
depth = "dashboard"
object.kind = "project"
```

The Dashboard must not:

* access `NavigationController`'s private state;
* call `resolvePaging()`;
* call `resolveUp()`;
* call `resolveTop()`;
* construct navigation destinations itself.

If the Dashboard needs to initiate navigation, it uses the controller's public action methods.

---

### D. Record acquisition

Once the active `project_id` is known, the Dashboard obtains records from the injected `ProjectRecordProvider` and identifies the corresponding `ProjectRecord`.

The Dashboard does **not** receive records through `NavigationController`.

The Dashboard also does not create a second data source.

This preserves the **Single Source of Truth** principle.

---

### E. ProjectRecord status contract

The Dashboard must respect the existing `ProjectStatus` vocabulary:

```text
possible
planned
current
completed
```

It must not invent additional status meanings.

The record contract establishes these content tiers:

| Status      | Required Dashboard-relevant data                                                              |
| ----------- | --------------------------------------------------------------------------------------------- |
| `possible`  | name, status, focus                                                                           |
| `planned`   | name, status, focus, milestone, progress, next_action, blockers, last_updated                 |
| `current`   | name, status, focus, milestone, progress, next_action, blockers, last_updated, repo_reference |
| `completed` | name, status, focus                                                                           |

The exact visual treatment remains open.

---

### F. Blocker semantics

This is a **frozen behavioral requirement**, not a design preference.

For `planned` and `current` records:

* `blockers === null` means **explicitly no blockers**;
* `blockers === undefined` is invalid at those tiers;
* `blockers` containing strings means blockers exist.

The Dashboard must not render `null` as though the field were missing.

In other words:

> **Valid absence is different from missing data.**

---

### G. Validation boundary

`validateProjectRecord()` owns ProjectRecord validation.

The Dashboard must not duplicate those validation rules.

If invalid data reaches the Dashboard, Phase 4 must define an explicit handling path rather than silently presenting misleading content.

The exact UI for invalid records remains an open decision.

---

### H. Missing-record behavior

A navigation state can theoretically identify a project while the provider fails to supply a matching record.

The supplied architecture does not currently define the UI behavior for that case.

Therefore the requirement we freeze is:

> **A missing ProjectRecord must never silently become a fabricated, stale, or misleading Dashboard.**

The precise failure presentation remains open.

---

### I. Rendering/lifecycle model

The Dashboard is a passive child view.

It should expose:

```text
render()
```

`CommandCenterView` controls when that method is called.

The Dashboard must not independently subscribe to navigation state or create an application-wide render loop.

This incorporates the established Slice 6/7 architectural pattern.

---

### J. Flag #2 consequence

The finalized Flag #2 decision also applies here.

The Dashboard's state-change callback, if required by its interaction contract, uses **constructor injection** rather than the old nullable setter-injection pattern.

The Phase 4 implementation must therefore not introduce the deprecated pattern:

```text
callback = null
setOnStateChange(...)
callback?.()
```

If the Dashboard needs to notify its owner, that callback is part of its required constructor contract.

### **Step 4A — Is the Phase 4 Dashboard read-only, or does it have a ProjectRecord editing responsibility?**

Yes. I think that's the right boundary, and it actually gives us a much cleaner Phase 4 decision.

### That gives us three categories

and contain a repository reference.

milestone

It may create and modify its own project-management metadata, notes, AI assignments, decisions, and operational context. That fits extremely well with the Project Bible's **Single Source of Truth**, **Simplicity over complexity**, and **AI assists the human architect** principles.

It also prevents a potentially nasty future problem: someone eventually deciding that because Command Center knows a repository location, it should also have filesystem/Git access and start becoming a second development environment.

## Step 4B — Define the editable Command Center metadata boundary

I think we can make this fairly tight.

The key question is not **“What can the user edit?”** in the abstract.

It is:

> **What information belongs to Command Center itself, as opposed to information belonging to the underlying project?**

### 1. Command Center-owned metadata

These are reasonable candidates for direct editing inside Command Center:

* **Project status**
* **Focus**
* **Milestone**
* **Progress**
* **Next action**
* **Blockers**
* **Project notes**
* **AI assignments/roles**
* **AI handoff/context notes**
* **Command Center decisions**
* **Operational links/references**
* **Last-updated metadata**

These describe **how Kurt is managing the project**, rather than modifying the project artifact itself.

### 2. Project-owned information

These should remain outside Command Center's editing authority:

* source code
* project configuration
* repository contents
* source assets
* application data
* tests
* build artifacts
* Git history
* project-specific files

Command Center can **reference** these things, but shouldn't edit them.

### 3. One subtle distinction: `name`

`ProjectRecord.name` is currently required, but we haven't established who owns changing it.

I would **not automatically make it editable in Phase 4**.

A project's name is closer to **project identity** than operational metadata. If we allow it to change casually, that can create problems with references and external systems.

So I'd currently classify:

So I'm now thinking the high-level CC project categories should probably evolve toward something like:

**Possible** → ideas and exploratory projects
**Planned** → projects we've decided to pursue but haven't actively started
**Current** → projects we're actively working on now
**Ongoing** → established projects that remain alive but aren't necessarily current priorities
**Archived** → projects intentionally retired or preserved for historical reference

## Step 4J — Canonical vs. Contextual Information

This is an important architectural boundary, because Command Center is going to accumulate a **lot** of information about each project.

We don't want:

> `Project.md` says one thing
> `AI_Context.md` says another
> Dashboard says something else
> GitHub says something else

So the rule should be:

> **Every important fact has one authoritative home. Command Center may display or reference it elsewhere, but should not create competing copies of the fact.**

### Three categories

#### 1. Canonical project data

This is the small set of structured facts that define the project's current identity/state.

Examples:

* `project_id`
* name
* status
* focus
* milestone
* progress
* next action
* blockers
* last updated
* repository reference

This belongs to the **ProjectRecord**.

---

#### 2. Command Center contextual information

This is information that helps you understand and operate the project but doesn't belong in the minimal ProjectRecord.

Examples:

* project purpose/background;
* product direction;
* technical stack;
* tools/environment;
* AI team and roles;
* ecosystem/workstreams;
* important notes;
* handoffs;
* historical context;
* decisions.

This belongs in the **Project Workspace**.

---

#### 3. Externally authoritative information

Some facts belong to other systems.

Examples:

| Information                    | Authority                 |
| ------------------------------ | ------------------------- |
| Source code                    | Git repository            |
| Git history                    | Git                       |
| Actual Obsidian vault contents | Obsidian/files            |
| Payment/account state          | Relevant external service |
| Website's deployed state       | Hosting/deployment system |
| AI conversation history        | AI platform/conversation  |

Command Center can **link to, summarize, or expose** those things, but shouldn't pretend its copy is the authoritative source.

### Why this matters for our read-only model

Suppose CC displays:

> **Repository:** `kurt-engine-core`

That doesn't mean CC owns the repository.

It means:

> "Here's where the authoritative engineering resource lives."

Likewise, if CC displays:

> **Python**

that's a project-context fact maintained by CC.

If the repository later changes from Python to TypeScript, **that becomes something we deliberately update in the project context** rather than expecting CC to magically become the source of truth for the repository's technology.

> `Teacher Toolbox — Ongoing`

must **not** require moving the project's files or workspace from one physical folder to another.

The project remains where it is. Only its status changes.

So we should **not** implement the project structure as:

```text
Current/
   Teacher_Toolbox/

Ongoing/
   Teacher_Toolbox/
```

because changing status would require physically relocating the project.

Instead, conceptually:

```text
Projects/
├── Teacher_Toolbox/
│   ├── Project.md
│   ├── Notes/
│   ├── Decisions/
│   └── ...
│
├── Kurts_English/
│   └── ...
│
└── Command_Center/
    └── ...
```

and the project record says:

```text
Teacher_Toolbox
status: current
```

CC's **Current** view simply queries for projects whose status is `current`.

If you change it to:

```text
status: ongoing
```

the physical project remains exactly where it was; it simply disappears from **Current** and appears in **Ongoing**.

### This is an important architectural principle

> **Project status must be represented independently of physical file/folder location. Status changes must not require moving, renaming, or restructuring the project's files or workspace.**

That gives us several benefits:

* no broken links;
* no Git disruption;
* no accidental file moves;
* no duplicated project folders;
* simpler project-wide search;
* stable project identity;
* easy status changes;
* much better portability.

And it reinforces something we've already established:

**The Command Center's views are projections of project state, not physical representations of project state.**

That's a pretty important piece of the architecture.

The remaining open question is really just the **exact transition rules**. Everything else you've raised has converged nicely.

## Step 4N — Category 4: Operational State

How far along that milestone/workstream is.

## Step 4P — Category 7: Documents, Files, Source Code & Search

This is another category where your earlier comments give us a pretty clear direction.

The key idea is:

> **Command Center is a project information/control center, not a file editor or IDE.**

### 1. Read-only access is a core capability

* Markdown
* `.ts`

* `.py`

> "It was successfully completed."

That is a much better semantic fit.

## Step 4T — Category 11: Project Notes, Decisions, History & Re-entry Context

This is where I think **Command Center really earns its existence**.

The Project Record tells us *what a project is and where it stands*. The notes/history layer tells us **why it is where it is**.

You should be able to add notes directly in CC about a project.

Examples:

* ideas
* observations
* questions
* research findings
* reminders
* decisions
* things an AI suggested
* things you want to investigate later
* explanations of why something was done

These are **CC-owned information**, so this is one of the places where the otherwise read-only CC model permits editing.

### 2. Decisions should be preserved

A particularly important type of note is a **Decision**.

For example:

```text id="6q0b5c"

Use Obsidian as the initial platform for Command Center.

Reason
It provides a fast way to build the visual operational
environment while keeping the underlying data in Markdown.

Future consideration
CC should remain portable to another platform.
```

That gives future-you the answer to:

> "Why the hell did we do it this way?"

rather than forcing you to reconstruct the reasoning from old conversations.

### 3. AI contributions should be attributable

This connects directly to your AI-team idea.

A note might say:

```text id="g5q7y2"
2026-08-...

CONCERN
Potential issue with ...

KURT'S DISPOSITION
Investigated — remains a Flag.
```

The AI doesn't become the authority.

But its contribution isn't lost.

We should preserve significant project history rather than continually overwriting the current state.

For example:

```text id="c8z4p1"

2026-07-24
Technical direction changed:
Web app first, standalone app eventually.

2026-07-29
Claude raised two architectural Flags.

2026-08-01
Flags reviewed and retained for further investigation.
```

That is enormously valuable for project re-entry.

I don't think every tiny action needs to become permanent history.

The distinction should be:

**Current State**

> What is true now?

**Notes**

## Step 4Z — Category 17: Ideas & Planning

This is where I think the distinction between **Ideas** and **Projects** becomes important.

### Ideas

**Ideas are not necessarily projects yet.**

They can be rough, incomplete, and messy.

An Idea might contain:

* a title;
* a short description;
* random notes;
* links;
* questions;
* possible uses;
* related ideas;
* AI-generated suggestions;
* references to existing projects.

For example:

```text
IDEAS

iCanMath
  "Possible math worksheet generator."

Mobile Kurt Engine
  "Eventually turn the homepage editor into a real app."

AI Workbench
  "Could become a reusable AI development environment."
```

There should be **no requirement that an Idea have Purpose, Focus, Milestones, Progress, etc.**

Those belong to a more mature Project Record.

### Planning

Planning is different.

A project in Planning is already sufficiently real that you've decided:

> **This is a project we're preparing to undertake.**

So it can have the full Project Record structure:

* Purpose
* Description
* Focus
* Status
* Milestones
* Next Action
* Flags
* Blockers
* Tools
* Resources
* Notes
* Decisions
* etc.

But it isn't necessarily being actively worked on yet.

### Ideas can become Projects

Eventually:

```text
IDEA
  ↓
[Promote to New Project]
  ↓
PROJECT RECORD
  ↓
Planning
```

But **promotion should not destroy the original idea notes**.

The new Project Record could retain:

> Originated from Idea: iCanMath

That gives us history right from the beginning.

### An Idea can also simply remain an Idea

This is important.

We shouldn't create artificial pressure to turn every idea into a project.

Some ideas are useful simply because they're recorded.

Others may eventually be discarded.

Others may merge into an existing project.

For example:

> "Mobile version of Kurt Engine"

might eventually become:

> a feature/tentacle of Kurt Engine

rather than its own project.

### Planning can also return to Ideas

Because you're the Project Owner, nothing requires a one-way progression.

You might decide:

> "We're not ready to make this a real project after all."

The project can return to an Idea state, while preserving what was learned during planning.

## Step 4AA — Category 18: Project Workspace Editing & Permissions

This is where we define the boundary between **Command Center information** and the **external project files** we've already discussed.

The basic principle now looks like:

> **CC can be edited as a project-management system. Project artifacts remain externally managed.**

### 1. Kurt / Project Owner can edit CC information

Inside a Project Workspace, the Project Owner should be able to change things such as:

* Purpose
* Description
* Focus
* Status
* Categories
* Next Action
* Notes
* Decisions
* Flags/dispositions
* Project relationships
* Tools
* AI roles
* Source references
* Progress, if they want to override an AI estimate

This is the actual editable part of CC.

### 2. Authorized AI can edit designated operational information

An AI should be able to maintain things such as:

* session notes;
* where work stopped;
* what was accomplished;
* current focus;
* estimated progress;
* recommended next action;
* technical observations;
* Flags it raises.

The AI's changes should be distinguishable where useful.

For example:

```text id="q4r7m2"
Progress
~70%

AI estimate — Claude
Updated: Aug. 17
```

You don't have to personally calculate the percentage.

### 3. Some CC information remains Project Owner-controlled

AI can **suggest** changes to these, but shouldn't silently make them:

* Project Status
* Purpose
* fundamental Description
* Category
* major architectural Decisions
* final Flag disposition
* whether something is a Blocker
* whether a project should be Archived

This gives us the distinction:

**AI maintains operational context.**

**Project Owner governs the project.**

### 4. External project files remain outside this editing model

If CC displays:

```text
kurt-engine-core/
    src/
       command-center-view.ts
       orientation-bar.ts
```

you can read, search, highlight, and copy that code.

But CC doesn't become the editor.

If something needs changing:

> **Open it in the appropriate development tool.**

That could be VS Code, another IDE, GitHub, or eventually Codex/another implementation system.

### 5. The same principle works for non-code projects

For a construction project, CC might display:

```text
Project Documents
    Building Plan.pdf
    Contractor Quote.pdf
    Permit.pdf
```

You can inspect those documents through CC.

But CC isn't secretly becoming an architectural CAD system or PDF editor.

For a business plan:

```text
Business Plan.md
Market Research.pdf
Financial Model.xlsx
```

Again, CC provides **context, access, search and organization**, rather than trying to replace every specialized application.

### 6. The Project Workspace should make the boundary obvious

I think the UI should eventually distinguish:

**CC Information**

> Editable here.

from:

**Project Files / Sources**

> Read / Search / Copy / Open externally.

That will prevent the user from wondering:

> "Am I editing the actual project file or just adding a CC note?"

## Step 4AB — Category 19: Flags, Blockers & Attention Management

We've already made an important distinction here:

> **Flags and Blockers are not the same thing.**

### 1. Flags

A **Flag** is a potential concern that deserves attention.

It does **not** necessarily mean the project cannot proceed.

Examples:

* AI notices a possible architectural problem.
* A decision may create problems later.
* Something hasn't been verified.
* Two project documents appear inconsistent.
* A dependency may become an issue.

A Flag should be **prominent enough that it doesn't disappear into ordinary notes**.

For example:

```text id="x8q4mv"
⚑ FLAGS — 3

⚑ Possible architectural conflict
   Raised by: Claude

⚑ Repository structure may complicate portability
   Raised by: GPT-5.6

⚑ Third-party dependency needs verification
   Raised by: Claude
```

### 2. Blockers

A **Blocker** means something is currently preventing progress.

For example:

```text id="7p2n5c"
⛔ BLOCKERS — 1

⛔ Cannot proceed with Phase 4 until
   repository access issue is resolved.
```

That is materially different from:

> "This might cause trouble later."

### 3. AI can raise Flags

This is one of the places where AI should have genuine authority to **add information to CC**.

If Claude finds something concerning:

> Claude doesn't need to ask permission to create the Flag.

It can record:

* what it noticed;
* why it matters;
* which project/file/decision it relates to;
* who/what raised it;
* when it was raised.

But the AI shouldn't automatically convert it into a Blocker.

### 4. The Project Owner determines disposition

The Project Owner can decide:

```text id="z1d8rq"
Flag
   ↓
Investigate
   ↓
┌──────────────┬──────────────┬──────────────┐
│              │              │              │
Dismiss       Accept       Convert to      Keep Open
                          Blocker
```

And "Keep Open" is important.

You don't necessarily need to resolve a Flag immediately.

### 5. A Flag can become a Blocker later

For example:

```text id="6f3m1w"
Aug 10
⚑ Claude identifies possible dependency problem.

Aug 12
Investigated.

Aug 14
Confirmed.

⛔ Converted to Blocker.
```

That history is valuable.

### 6. Blockers should be prominent

A Blocker should never be buried inside a project note.

The workspace should make it visually obvious that:

> **Something is preventing progress.**

But I wouldn't necessarily make the entire Dashboard revolve around them. The Home Screen can simply surface that attention exists; the Project Workspace contains the details.

### 7. Flags shouldn't become clutter

There should eventually be some mechanism for:

* active Flags;
* dismissed Flags;
* resolved Flags;
* converted Blockers.

But the historical record should remain searchable.

That way an old Flag doesn't clutter the active workspace forever, while still remaining part of the project's history.

| ID      | Requirement                                                                                                     | Status                    |
| ------- | --------------------------------------------------------------------------------------------------------------- | ------------------------- |

| P4-R259 | A Flag represents a potential concern requiring attention but not necessarily preventing progress.              | **Established**           |
| P4-R260 | A Blocker represents an issue currently preventing or materially stopping progress.                             | **Established**           |
| P4-R261 | Authorized AI may raise Flags based on its observations.                                                        | **Established**           |
| P4-R262 | AI should not automatically classify a Flag as a Blocker.                                                       | **Established**           |

### Category 19 verdict

I think this gives us the terminology we've been circling around:

**Flag = "Pay attention to this."**

**Blocker = "We can't proceed until this is dealt with."**

And importantly, **the AI can bring something to your attention without pretending it knows whether the problem is serious enough to stop the project.**

## Step 4AC — Category 20: Search & Knowledge Retrieval

This is one of the more important pieces because CC is eventually going to contain **a lot of accumulated information**.

The basic principle:

> **If the information is in CC or an authorized project source, you should be able to find it without remembering where it lives.**

### 1. One Search button

We've already settled on this:

```text id="7q2m4k"
[ SEARCH ▼ ]
```

The dropdown determines the scope:

```text id="c5n8wp"
File
Project
```

### 2. File Search

**File** means:

> Search the contents of files/documents.

That includes source code.

For example:

```text id="2w8r1f"
SEARCH: "onStateChange"

Results

command-center-view.ts
  line 47

category-view.ts
  line 82

project-list-view.ts
  line 91
```

Selecting a result should take you directly to the relevant portion of the file where practical.

And, as we established earlier, you should be able to:

**see → highlight → copy**

the result/content.

### 3. Project Search

**Project** means:

> Search the information associated with projects.

That could include:

* Purpose
* Description
* Focus
* Notes
* Decisions
* Flags
* Blockers
* History
* AI session notes
* tools
* technical information
* source references
* related projects
* seeds

For example:

> Search `premium access`

could find:

```text
Teacher Toolbox
  Notes
  Business considerations
  iCanSpell
  Marketing
  Account management

Archived project
  Earlier discussion of premium access
```

### 4. Search should cross project status

Search shouldn't stop at Current.

If you're looking for something from an old project, it should be possible to find it in:

* Current
* Planning
* Ideas
* Ongoing
* Archived

That's particularly important because **Archived is a knowledge repository, not a dead end.**

### 5. Search should eventually understand relationships

A particularly useful future capability would be searching not only text, but project relationships.

For example:

> "Show me everything related to iCanSpell."

could potentially return:

```text
Teacher Toolbox
├── iCanSpell notes
├── Premium access
├── Marketing
├── Account management
└── Related decisions

Possible Future Project
└── iCanSpell standalone version

Archived
└── Earlier worksheet-generator experiments
```

That's beyond simple keyword search, so I'd classify it as a **future capability**, not something we need to solve now.

### 6. AI should use the same retrieval system

This is where Search connects directly to our AI architecture.

An authorized AI shouldn't need a completely separate secret database of CC information.

It should be able to search/retrieve the same underlying project information.

That means:

> **Kurt and the AI are looking at the same source of project truth.**

The AI may interpret it differently, but it isn't working from a private copy.

### 7. Search results should show provenance

A result should make it clear **where the information came from**.

For example:

```text id="1p6v9x"
Teacher Toolbox
  → Decisions
  → Premium Access
  → Decision 2026-07-24

GitHub
  → src/account-service.ts
  → line 118
```

This is especially important when AI is using the information.

> **"Where did I put that?"**

And eventually:

> **"What do we know about this?"**

That becomes especially valuable as the number of projects, archived projects, notes, decisions, seeds, and external documents grows.

Next is **Category 21 — Templates & Project Seeds**.

We've already established the basic distinction, but now we should define how these two mechanisms actually relate to **New Project**.

### Step 4AD — Templates & Project Seeds

We have two fundamentally different starting points.

#### Template

A **generic starting structure**.

Examples:

* General Project
* Software Project
* Business Plan
* Construction Project
* Conference/Event
* Research Project
* Content/Media

A template doesn't come from a specific past project.

It says:

> "Here's a useful structure for this *type* of project."

#### Project Seed

A **proven starting point derived from an existing project**.

For example:

> "This particular project structure/code/document set worked well. Let's reuse it."

A seed might contain:

* code;
* folder structure;
* documents;
* configuration;
* research;
* processes;
* lessons learned;
* proven components.

### New Project should eventually offer both

```text id="gq7r2x"
NEW PROJECT

How do you want to start?

[ Blank Project ]

[ Template ]
     ↓
   Choose template

[ Project Seed ]
     ↓
   Choose seed
```

But there's another possibility we've already established:

### A Project Canvas can begin inside Ideas

This is important.

You might select:

> **New Project → General Project Template**

and CC creates a **Project Canvas** in Ideas.

You can then freely brainstorm:

```text id="q0n6mz"
PROJECT CANVAS

Name: iCanMath

Purpose:
[ still figuring this out ]

Ideas:
• ...
• ...
• ...

Questions:
• ...
• ...

Possible Tools:
• ...
```

It doesn't become a formal Planning project until **you decide it is ready**.

### Seeds can therefore enter the same process

For example:

```text id="e7v1s4"
Archived Project
       ↓
   Create Seed
       ↓
New Project Canvas
       ↓
Ideas / experimentation
       ↓
Planning
```

So a seed isn't necessarily an instant clone.

It can be a **starting point for exploration**.

### Seeds should be referenceable

If you eventually create a project from a seed, CC should preserve the relationship:

```text id="b8n3yq"
Project: New Homepage Tool

Origin
Seeded from: Kurt Engine Core
```

That gives you useful lineage without merging the two projects.

### Seeds should be independently reusable

One archived project could produce multiple seeds.

And one seed could potentially be used to create multiple projects.

```text id="6k5w2p"
Kurt Engine Core
      │
      ├── Seed: Homepage Architecture
      │       ├── Project A
      │       └── Project B
      │
      └── Seed: Deployment Structure
              └── Project C
```

That's another reason **Seed** shouldn't simply mean "copy the whole old project."

## Step 4AE — Category 22: Project Relationships / The "Tentacles"

This is one of the things I think makes **Command Center fundamentally different from a simple project tracker**.

A project isn't necessarily one thing.

It can have a whole ecosystem growing around it.

### Example: iCanSpell → Teacher Toolbox

You gave the perfect example earlier.

A project that begins as:

> **iCanSpell — worksheet generator**

can eventually generate questions about:

* user accounts
* free vs. premium access
* payments
* marketing
* licensing
* hosting
* customer support
* privacy
* distribution
* mobile apps
* related products

Those aren't necessarily all part of the original coding project.

They're **tentacles extending from it**.

### CC should represent those relationships

Conceptually:

```text id="p3x8q1"
                    TEACHER TOOLBOX
                          │
          ┌───────────────┼────────────────┐
          │               │                │
      iCanSpell        iCanMath        iCanCreate
          │
     ┌────┼─────┬────────┐
     │    │     │        │
 Accounts Payments Marketing Licensing
```

And those related items don't necessarily need to be separate projects.

Some might be:

* **sub-projects**
* **workstreams**
* **components**
* **dependencies**
* **related projects**
* **external services**
* **business concerns**
* **research areas**
* **future ideas**

We shouldn't force everything into one relationship type.

### The relationship itself needs a type

For example:

```text id="2q6w9m"
Teacher Toolbox
   └── iCanSpell
       Relationship: Product / Component

iCanSpell
   └── Stripe
       Relationship: External Service

iCanSpell
   └── Premium Access
       Relationship: Business Workstream

iCanSpell
   └── Mobile Version
       Relationship: Future Extension
```

That lets CC represent the real structure without pretending everything is a conventional "project."

### A related item can have its own life

This is important.

Suppose:

> **Mobile Version of iCanSpell**

starts as an Idea.

Later it becomes a formal project.

Eventually it could have its own:

* Purpose
* Status
* Notes
* Decisions
* Flags
* Repository
* AI team
* Seeds

It remains connected to iCanSpell, but becomes independently manageable.

So the relationship becomes:

```text id="5y0n4k"
Teacher Toolbox
      │
      └── iCanSpell
              │
              └── Mobile iCanSpell
```

## Step 4AH — Category 25: Project Files & Read-Only Access

This is the area that directly addresses your `.ts` problem.

The goal is simple:

> **CC should let you inspect project files without requiring you to open VS Code just to see what's inside them.**

### 1. Files are part of the Project Workspace

A project could have a **Files** entry alongside the other project information.

Selecting it opens the project's accessible files.

```text id="7m4q2x"
FILES

src/
├── command-center-view.ts
├── project-list-view.ts
├── category-view.ts
└── orientation-bar.ts

docs/
├── architecture.md
└── decisions.md
```

### 2. `.ts` files are code, not videos

CC should identify files based on their actual file type/extension rather than relying on macOS Finder's default application association.

So:

```text id="h8p3v1"
command-center-view.ts
Type: TypeScript
```

should be treated as **source code**.

Likewise:

```text id="w6n2k9"
build.py
Type: Python

README.md
Type: Markdown

architecture.json
Type: JSON
```

### 3. Open a file → see the actual contents

You shouldn't have to launch VS Code.

For example:

```text id="4r9c7m"
command-center-view.ts

────────────────────────────────────────

export class CommandCenterView {
    ...
}

────────────────────────────────────────

[ Search in file ]   [ Copy ]
```

The important part is that you're looking at the **actual file**, not a CC-generated summary.

### 4. Highlight and copy

This was one of your specific requirements.

You should be able to:

> **see → highlight → copy**

code or text from a file.

So if I ask you:

> "Show me the `command-center-view.ts` constructor."

you can open it in CC, highlight the relevant section, and copy it directly into the chat.

That eliminates the current:

> Finder thinks `.ts` is a video → somehow get it into VS Code → find the code → copy it.

workflow.

### 5. Read-only means genuinely read-only

For the initial CC implementation, opening a project file should **not accidentally modify it**.

The file viewer should be an inspection surface.

Possible controls:

```text id="1p6k3z"
[ Search ]   [ Copy ]   [ Open Externally ]
```

Not:

```text
[ Save ]
[ Modify ]
[ Rename ]
```

The actual file remains under the control of the filesystem/repository and its normal development tools.

### 6. "Open Externally" is still important

Sometimes you *do* want VS Code.

So CC could provide:

> **Open Externally**

which hands the file to its normal application.

For a `.ts` file:

> Open in VS Code.

For a PDF:

> Open in Preview.

For an image:

> Open in Preview.

CC becomes the **inspection/navigation layer**, not a replacement for every application.

### 7. Search works inside the file

This connects directly to our Search category.

If you're viewing:

```text id="z5k8n2"
command-center-view.ts
```

you should be able to search:

> `onStateChange`

and jump to each occurrence.

That's different from **Project Search** or **Disk Search**.

It's a search *within the currently opened artifact*.

### 8. Files don't have to be physically inside the project folder

This is important given our Disk Search discussion.

A Project Record can contain references to files located elsewhere.

For example:

```text id="q1v7m4"
Teacher Toolbox

Associated Files
├── ~/Projects/TeacherToolbox/src/...
├── ~/Downloads/new-business-plan.pdf
└── ~/Desktop/research-notes.md
```

The physical locations don't have to change just because CC knows they're relevant.

The exact schema can evolve, but the important thing is:

> **The Decision is the authoritative record.**

The conversations that led to it are supporting evidence.

### This solves an important AI problem

A new AI shouldn't have to read five old conversations to discover:

> "What did we actually decide?"

CC can give it the Decision directly.

Then, if the AI needs to understand **why**, it can follow the supporting references back to the relevant threads.

### Decisions should have states

Not everything discussed becomes a permanent decision.

We could eventually distinguish:

* Proposed
* Under Review
* Established
* Superseded
* Rejected

But **Kurt remains the arbiter** of when something becomes an established project decision.

AI can recommend:

> "I think this should become an established decision."

It doesn't make that authoritative by itself.

### Decisions can be superseded without destroying history

For example:

```text id="q7n3m5"
D-042
Setter injection

      ↓ superseded by

D-071
Constructor injection
```

D-042 remains in the historical record.

That is much better than editing D-042 until it looks like it was always D-071.

### Architectural decisions deserve special treatment

Not every decision is equally important.

A project might have:

```text id="k2v8p4"
PROJECT DECISIONS

Architecture
D-042 — Injection pattern
D-051 — State ownership
D-063 — Repository model

Implementation
D-067 — File viewer approach

UI
D-070 — Navigation structure
```

This is particularly valuable for the Command Center itself because **frozen architectural decisions should not casually be reopened during implementation**.

## Step 4AM — Category 30: Project History / Audit Trail

This is the **"what happened?"** layer.

We've now separated current state from historical context, so History should not become another dumping ground for everything.

### 1. History records meaningful events

Examples:

```text id="5k8p2m"
PROJECT HISTORY

Aug 16
• Project status changed: Planning → Current
• Decision D-071 established
• Flag F-014 raised by Claude

Aug 17
• Category 25 completed
• GPT session updated Where Things Stand
• Handover created: GPT-5.5 → GPT-5.6

Aug 18
• Repository source added
• Local workspace linked
```

The point is not to record every keystroke.

It's a **meaningful event trail**.

### 2. History should preserve provenance

Every meaningful event should ideally answer:

> **What happened? Who/what caused it? When?**

For example:

```text id="7q3m9v"
EVENT

What:
Flag F-014 raised

When:
Aug 17, 2026

Source:
Claude — Command Center Implementation

Thread:
[Thread Reference]

Actor:
Claude

Related:
Project: Command Center
```

The actor could be:

* Kurt
* GPT
* Claude
* Qwen
* an Agent
* CC itself
* an external integration

### 3. AI changes should be distinguishable from human decisions

This is important.

If Claude updates:

> Where Left Off

that's different from **Kurt establishing an architectural Decision**.

History should make that visible.

```text id="q4m8n1"
AI ACTION
Claude updated Where Things Stand.

vs.

HUMAN DECISION
Kurt established D-071.
```

### 4. History should not be editable like ordinary notes

The whole value of History is that it represents what happened.

So ideally:

> **Events are append-only.**

If something needs correction, you add another event:

```text id="z6p2k8"
Aug 17
Incorrect status recorded.

Aug 17
Correction: status was actually Planning.
Corrected by Kurt.
```

You don't rewrite the original event and pretend it never happened.

### 5. History should be filterable

A project could eventually have a lot of history.

Useful filters might include:

```text id="2v7m4q"
[ All ]

[ Kurt ]
[ AI ]
[ Agent ]

[ Decisions ]
[ Status Changes ]
[ Flags ]
[ Blockers ]
[ Handovers ]
[ Files ]
[ Sources ]
```

That would make the history useful instead of overwhelming.

### 6. History connects the other CC systems

This is where the model starts becoming powerful.

A Decision can point to:

> supporting threads → handover → history

A Flag can point to:

> AI thread → file → decision

A project status change can point to:

> Kurt → reason → history

So History becomes the **chronological connective tissue** between the other project artifacts.

| ------- | -------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------- |

| P4-R443 | History should record meaningful project events rather than every low-level interaction.                                               | **Established**                           |
| P4-R444 | Meaningful events should preserve timestamp, actor/source, and relevant project/artifact relationships where available.                | **Established direction**                 |
| P4-R445 | History must distinguish human actions, AI actions, Agent actions, and CC/system actions where applicable.                             | **Established direction**                 |
| P4-R446 | Historical events should be append-only or otherwise preserve their original state.                                                    | **Established architectural requirement** |
| P4-R447 | Corrections should be recorded as subsequent events rather than silently rewriting history.                                            | **Established**                           |
| P4-R448 | Project History should support filtering by event type and actor.                                                                      | **Future capability**                     |

### Category 30 verdict

We're now getting a clean separation:

**Where Things Stand**
→ *What is happening now?*

**History**
→ *What happened?*

**Decisions**
→ *What was deliberately decided?*

**Threads / Handovers**
→ *Where did the discussion/context come from?*

**Sources / Files**
→ *Where is the actual material?*

That separation is going to keep CC from turning into one giant undifferentiated project notebook.

## Step 4AN — Category 31: Project Relationships & "Tentacles"

This is the category that addresses something you identified very early:

> **A project is rarely just one thing.**

Your iCanSpell → TeacherToolbox example is a perfect illustration.

The original project may start as:

> **iCanSpell**

Then questions appear about:

* accounts
* subscriptions
* premium access
* payments
* marketing
* customer support
* hosting
* legal
* documentation

Some of those may eventually become projects in their own right.

CC needs to represent those relationships without forcing everything into one giant project.

### 1. Projects can relate to other projects

For example:

```text id="6p3m8q"
TeacherToolbox
      │
      ├── iCanSpell
      ├── iCanMath
      ├── iCanCreate
      └── iCanToolbox
```

But that's only one type of relationship.

### 2. Relationships should have meaning

Instead of simply:

> Related Project: iCanSpell

we could eventually distinguish:

```text id="v7n2k4"
TeacherToolbox
   │
   ├── contains → iCanSpell
   ├── depends on → Payment System
   ├── uses → Authentication Service
   ├── related to → Marketing Project
   └── derived from → iCanSpell Prototype
```

The exact vocabulary can evolve.

The important architectural decision is:

> **A relationship has a type.**

### 3. "Tentacles" don't have to become projects

This is important.

You may discover:

> "We need to figure out how premium accounts will work."

That doesn't automatically mean:

> Create another project.

It might initially just be:

* a Note
* a Flag
* a Task
* a research question
* a Decision candidate

Only if it grows into something substantial does it need to become its own project.

### 4. Projects can spawn projects

For example:

```text id="p4w8m2"
iCanSpell
    │
    ├── spawned →
    │       Premium Accounts
    │
    ├── spawned →
    │       Payment Infrastructure
    │
    └── spawned →
            Marketing System
```

And importantly, the original project doesn't disappear.

It remains the parent/contextual source.

### 5. Projects can share resources

For example:

```text id="n8q3v7"
TeacherToolbox
      │
      ├── iCanSpell ─────┐
      │                  │
      ├── iCanMath ──────┼──→ Authentication
      │                  │
      └── iCanCreate ────┘
```

The authentication system might itself be a project, a service, or simply a shared resource.

CC should be able to represent that without forcing a rigid hierarchy.

### 6. Relationships can cross status boundaries

An **Ongoing** project can be related to an **Archived** project.

An **Idea** can originate from an **Ongoing** project.

A **Planning** project can depend on another **Ongoing** project.

And, as we established earlier, **status changes without moving the underlying project files**.

So relationships should point to **Project IDs**, not folders.

### 7. This is where Seeds become particularly useful

Suppose an old project is archived but contains an excellent foundation:

```text id="r5m9k2"
Archived Project
       │
       └── Seed
             ↓
       New Project
```

The new project can explicitly say:

> **Seeded From: Project X**

while preserving the historical relationship.

That's much better than copying files around and losing the lineage.

This gives us a much better model than a simple folder hierarchy.

**Projects form a network, not just a tree.**

And that fits your "tentacles" idea perfectly:

> **CC keeps track of the things that grow out of, depend on, connect to, or are derived from a project — without automatically turning every tentacle into another project.**

## Step 4AO — Category 32: Seeds & Project Lineage

This is the piece you emphasized earlier:

> **Archived does not mean dead.**

A project can be finished, abandoned, superseded, or simply no longer active — while containing something valuable enough to become the foundation of another project.

### 1. A Seed is an explicit reusable artifact

Think of a Seed as:

> **Something worth carrying forward.**

It could be:

* code
* architecture
* a template
* a business concept
* research
* a design
* documentation
* a workflow
* a partial implementation
* a proven solution to a particular problem

It does **not** have to be an entire project.

### 2. A Seed can come from anywhere

For example:

```text id="8q3m6v"
ARCHIVED PROJECT
TeacherToolbox Prototype
       │
       ├── Seed: Worksheet SVG renderer
       ├── Seed: Project structure
       └── Seed: Font/path handling
```

Those Seeds could later be used by completely different projects.

### 3. A Seed should preserve its origin

This is where lineage becomes important.

```text id="m7p2k9"
SEED

Name:
Worksheet SVG Renderer

Origin:
TeacherToolbox Prototype

Origin Project ID:
TT-001

Created:
...

Description:
Reusable SVG rendering approach.

Used By:
iCanSpell
Future Project X
```

So when you encounter the Seed five years later, you can still answer:

> **Where did this come from?**

### 4. Using a Seed creates another relationship

For example:

```text id="4v8n2q"
TeacherToolbox Prototype
        │
        └── Seed
              │
              ↓
          iCanSpell
```

The new project can say:

> **Built From Seed: Worksheet SVG Renderer**

rather than pretending that the technology appeared from nowhere.

### 5. A Seed doesn't have to be copied

This is important.

A Seed might be:

* referenced;
* copied;
* forked;
* adapted;
* imported;
* used as inspiration.

CC should eventually distinguish those relationships.

But the **original Seed remains intact**.

### 6. Seeds can become templates

This connects directly to your earlier idea of a future suite of project templates.

There are really two related concepts:

**Seed**

> Something extracted from an existing project because it may be useful again.

**Template**

> Something deliberately prepared as a starting point for a new project.

A Seed can eventually be promoted into a Template.

```text id="z5k8p3"
Archived Project
      │
      └── Seed
            │
            └── promoted to → Template
                              │
                              ↓
                         New Project
```

### 7. Seeds can preserve failed ideas too

This is another reason not to equate Archived with Completed.

A project might be abandoned because the approach didn't work.

But one component may still be useful.

For example:

> "This architecture didn't work for Project A, but this particular file-management technique was excellent."

That technique can become a Seed.

So **failure doesn't erase useful knowledge.**

This gives us a nice lifecycle:

**Project → Artifact → Seed → New Project**

without destroying the history of where anything came from.

And it reinforces why **Archived** is much better than **Completed**.

A project can be archived because its active life is over while still being an extremely valuable **source of future work**.

## Step 4AQ — Category 34: Tasks, Actions & Next Actions

This is the point where we connect **"Where Things Stand"** to actual work.

We've already established that CC should answer:

> **Where was I? How was I doing this? What do I do next?**

The **Next Action** is the bridge between project state and actually moving the project forward.

### 1. A Task is not the same thing as a Next Action

A project may have dozens of tasks:

```text id="6m8q2p"
TASKS

□ Research hosting options
□ Review Claude's proposal
□ Update project schema
□ Test repository linking
□ Decide status terminology
□ Build dashboard
□ Document handover process
```

But **Where Things Stand** should identify the immediate thing that matters:

> **Next Action: Decide status terminology.**

So:

**Tasks** = work that exists.

**Next Action** = the specific work that should happen next.

### 2. Next Action should be prominent

I'd keep it right alongside the existing project-state information:

```text id="8q4n7m"
WHERE THINGS STAND

Current Focus
Project lifecycle model

Next Action
Define Tasks / Actions model

Attention
⚑ Clarify whether Tasks can be AI-generated
```

Not buried in a separate task-management screen.

### 3. AI can help maintain Tasks

This fits what we established earlier.

An AI could say:

> "We've established the Project Template model. I recommend creating the next action: define the Task model."

It can **propose** that action.

You can accept it.

Or you can say:

> "No. I want to work on something else."

CC shouldn't decide your priorities for you.

### 4. AI can update task state

An AI might legitimately record:

> "Task completed: Document Handover Prompt."

But again, there's a distinction between:

**AI reporting that it completed something**

and:

**Kurt declaring that the project is complete.**

The former is operational data.

The latter is governance.

### 5. Tasks should be lightweight

I don't think CC needs to become another giant task-management application.

A task probably needs only:

```text id="p3v8k1"
TASK

Title:
Define Task model

Status:
Open

Priority:
Normal

Created:
...

Due:
(optional)

Project:
Command Center

Source:
GPT — Architecture thread

Notes:
...
```

We can add sophistication later if it proves useful.

### 6. Tasks can originate from anywhere

A Task might come from:

* Kurt
* AI
* Agent
* Decision
* Flag
* Blocker
* Project review
* Meeting
* external source
* another project

For example:

> Flag → Task to investigate

or:

> Decision → Task to implement

or:

> Meeting → several Tasks.

This is where CC starts becoming genuinely interconnected.

### 7. Tasks shouldn't automatically become Blockers

We've already established your distinction:

**Flag ≠ Blocker**

The same principle applies here.

A Task can address a Flag:

```text id="r7m2q9"
Flag
Potential architectural problem

        ↓

Task
Investigate the problem

        ↓

Decision
Keep / change architecture
```

But the Flag doesn't become a Blocker simply because a Task exists.

### 8. Tasks can be project-independent

Some future Tasks might be useful across projects.

But initially I'd keep the Project association optional rather than designing a complicated global task system.

The important thing is:

> **CC should not assume every task belongs to one physical project folder.**

The Project ID relationship is logical.

18 established

Last Review
Aug. 15

Current

That is much more honest and useful.

This is where AI becomes genuinely useful.

For example:

> "Three Flags have remained unresolved for more than two weeks."

> "The same task has been reopened twice."

> "Several AI threads are discussing the same unresolved architectural question."

## Step 4AT — Category 37: Files, Sources & External Locations

This one connects several things we've already established:

* projects don't move when their Status changes;
* files can accidentally end up outside the project;
* downloads may land in `Downloads`;
* repositories can be GitHub, local folders, iCloud, Google Drive, etc.;
* **Search** should find files wherever they actually are;
* CC itself should remain portable and not depend on one storage provider.

The key principle:

> **CC tracks where project material actually lives. It does not require the material to physically live inside the CC vault.**

### 1. A Project can have many kinds of Sources

For example:

```text id="6q3m8v"
PROJECT SOURCES

GitHub
  Command_Center
  [Open Repository]

Local
  ~/Desktop/Projects_Folder/Command_Center

iCloud
  ~/Library/Mobile Documents/...

Google Drive
  [Project folder]

External
  Conference registration portal
  [Open]

Files
  specification.md
  budget.xlsx
  floor-plan.pdf
```

The important distinction is that **Repository**, **Folder**, **File**, **Cloud Location**, and **External Link** are different source types.

### 2. The physical location is not the Project identity

This is important given our Status discussion.

A project might physically remain:

```text
Desktop/Projects_Folder/MyProject
```

while CC says:

```text
Status: Archive
```

Later you can reactivate it without moving anything.

The Project ID is the logical identity.

The physical location is simply a **Source** associated with that Project.

### 3. A file outside the project can still belong to the project

Your Downloads example is exactly the case.

Suppose Claude sends you:

```text
Downloads/WP13-review.md
```

It doesn't magically become part of the project just because its filename says WP13.

But CC's Search could discover it and show:

```text
SEARCH RESULT

WP13-review.md

Location:
Downloads/

Possible Project:
Command Center

⚠ Currently outside registered project locations

[Associate with Project]
[Move File]
[Ignore]
```

And **Associate with Project** would ideally *not* require moving the file.

That's an important distinction.

### 4. "Move File" should be a separate action

CC shouldn't assume that association means relocation.

You might deliberately keep something in Downloads.

So:

**Associate**

> "This file belongs to Command Center."

**Move**

> "Physically relocate this file."

Two different operations.

### 5. Search becomes much more powerful

Your earlier requirement was:

> Search should include **file, project, repository, disk...**

I'd expand that into a unified search model.

Search could return:

```text id="n8p4k2"
SEARCH: onStateChange

PROJECT
Command Center

FILES
orientation-bar.ts
category-view.ts

REPOSITORY
22cryys56p-beep/Command_Center

LOCAL LOCATION
Desktop/Projects_Folder/Command_Center

CHAT THREAD
GPT — WP13 Verification

DECISION
D-071 — State injection pattern
```

That's much closer to the way you actually work.

You're not always looking for "a project."

Sometimes you're remembering:

> "Where the hell was that file?"

or:

> "Which thread did we discuss that in?"

or:

> "Which repository contains this?"

CC should be able to help answer all of those.

### 6. External storage needs to be first-class

We should explicitly support the concept of a **Storage Provider**.

Examples:

* Local disk
* iCloud
* Google Drive
* Dropbox
* GitHub
* other Git hosting
* NAS
* external drive
* web service
* arbitrary URL

CC doesn't need to deeply integrate with all of them initially.

It just needs a model capable of representing them.

### 7. Offline/unavailable locations need honest states

Suppose a project points to:

```text

```

but the drive isn't connected.

CC shouldn't say:

> "Project files missing."

It should say:

> **Location unavailable — Buffalo drive not mounted.**

Likewise for a cloud provider when the integration isn't available.

That's another application of your **Honest Failure over Silent Degradation** principle.

## Step 4AU — Category 38: What Belongs Inside CC vs. What Gets Referenced

This is an important boundary.

We've designed CC to **know about projects and their resources** without requiring CC to physically contain those resources.

### 1. CC owns the Project Record

For each project, CC should own the **operational metadata**:

```text
Project
├── Identity
├── Purpose
├── Description
├── Focus
├── Status
├── Where Things Stand
├── Attention
├── Next Action
├── Decisions
├── Flags
├── Blockers
├── Deadlines / External Cutoffs
├── AI Participants
├── Chat Thread References
├── Handovers
├── Seeds / Lineage
└── Source References
```

That's the **Command Center representation of the project**.

### 2. CC doesn't necessarily own the project's actual files

A project might have:

```text
GitHub repository
Local project folder
iCloud documents
Google Drive
Dropbox
PDFs
Spreadsheets
Images
AI chat threads
External websites
```

Those remain where they actually belong.

CC stores the **reference**.

### 3. But some things really should live inside CC

Things that are specifically **CC's own operational records** should be inside the CC data model.

For example:

* Project Record
* Decision Record
* Flag
* Blocker
* Task
* Handover Record
* Handover Prompt
* Review
* Checkpoint
* Seed Record
* Source Record
* AI Context
* Thread Reference

These aren't merely external project material.

They're **CC's knowledge about the project**.

### 4. The distinction is therefore:

> **CC owns knowledge about the project.**

> **The project owns its actual working material.**

That's a very useful boundary.

### 5. What about copies?

Sometimes an external document may need to be copied into CC.

For example, a handover prompt might originally exist in a chat, but you deliberately save a copy into CC.

That's fine.

But CC should distinguish:

```text
ORIGINAL
ChatGPT conversation

REFERENCE
Thread URL

CC COPY
Handover Prompt.md
```

The copy should not magically become the authoritative original.

Its provenance should be recorded.

### 6. CC should avoid becoming a giant file warehouse

This is particularly important for your Mac.

We don't want:

> "Let's copy every project file into Command Center so CC can manage it."

That would undermine the whole architecture.

Instead:

```text
                 COMMAND CENTER
                       │
          ┌────────────┼────────────┐
          │            │            │
       Metadata      Links       Context
          │            │            │
          └────────────┼────────────┘
                       │
                  PROJECT FILES
             remain wherever they are
```

### 7. This also supports portability

Because the CC data itself is largely Markdown/structured data plus references, the entire Command Center can be moved from:

> Obsidian

to another platform later.

The underlying project files don't have to move with it.

That's exactly what we wanted from the original **Obsidian seed**:

> **Built on Obsidian, but not architecturally dependent on Obsidian.**

## Step 4AV — Category 39: AI Access, Authority & Permissions

This is the natural next piece now that we've established what CC owns and what it merely references.

The central question is:

> **What can an AI actually do inside Command Center?**

We've already established that AI should be able to **maintain certain CC information**, but it should not quietly become the project owner.

### 1. Four levels of AI authority

I think we need four distinct levels:

**Read**

> AI can inspect CC information.

**Propose**

> AI can suggest a change, Task, Flag, Decision, etc.

**Update**

> AI can directly modify certain operational records.

**Govern**

> AI can make authoritative project decisions.

And that last level should generally remain **Kurt-controlled**.

For example:

| Action                            | AI          |
| --------------------------------- | ----------- |
| Read Project State                | ✓           |
| Read Decisions                    | ✓           |
| Read Thread References            | ✓           |
| Propose a Flag                    | ✓           |
| Create a Task                     | ✓           |
| Update "Where Things Stand"       | ✓           |
| Record work it actually performed | ✓           |
| Establish architectural Decision  | Normally no |
| Change Project Status             | Normally no |
| Declare Blocker authoritative     | Normally no |
| Archive Project                   | No          |
| Delete project history            | No          |

### 2. But permissions should be configurable

We shouldn't hard-code:

> "AI can never do X."

Different projects will have different needs.

A future construction project might use an Agent to maintain schedules.

A software project might allow an Agent to update Tasks automatically.

A research project might have an AI maintaining a literature log.

So the architecture should support **AI roles/capabilities**.

For example:

```text id="8m4q2p"
AI PARTICIPANT

Claude

Capabilities:
✓ Read Project
✓ Read Sources
✓ Update Tasks
✓ Update Where Things Stand
✓ Create Flags
✗ Establish Decisions
✗ Change Project Status
✗ Delete History
```

### 3. Agents need their own authority model

This becomes particularly important because we've already decided Agents should be part of CC's AI layer.

An Agent might be given a very narrow job:

> "Monitor the project repository for changes and update the project record."

That Agent should not suddenly have permission to:

> change project status, delete records, or modify architecture.

So Agent permissions should be **scoped**.

### 4. AI actions should be attributable

If CC says:

> "Where Things Stand was updated."

we should know:

> **Who updated it?**

For example:

```text id="n7q3v8"
ACTION

Actor:
Claude / Agent-02

Action:
Updated Where Things Stand

When:
Aug. 17, 2026

Previous:
WP13 implementation underway.

New:
WP13 Phase 3 implementation underway.

Source:
Claude Thread Reference
```

That gives us the audit trail we just established.

### 5. AI should not impersonate Kurt

This is particularly important for Decisions.

If Claude recommends:

> "I think we should adopt constructor injection."

CC shouldn't record:

> **Kurt decided constructor injection.**

Instead:

```text id="p4m8k2"
AI RECOMMENDATION

Claude recommends:
Constructor injection.

Status:
Proposed

Awaiting:
Kurt's decision
```

Once you actually decide:

```text id="q8n3v6"
DECISION D-071

Decision:
Constructor injection.

Decided By:
Kurt
```

That's an important provenance boundary.

### 6. Permissions should be visible

Eventually, CC shouldn't hide these rules somewhere in configuration.

A project could have:

```text id="v5q2m8"
AI ACCESS

GPT-5.6 Luna
  Read: ✓
  Propose: ✓
  Update: ✓
  Govern: ✗

Claude
  Read: ✓
  Propose: ✓
  Update: ✓
  Govern: ✗

Agent — Repository Monitor
  Read: ✓
  Propose: ✓
  Update: Limited
  Govern: ✗
```

That makes it obvious **who is allowed to do what**.

## Step 4AW — Category 40: Automation & Triggers

Now that we've defined **what AI/Agents are allowed to do**, the next question is:

> **When should they do it?**

This is where automation comes in.

### 1. Automation should be event-driven

Rather than having an Agent constantly poking around CC, actions can be triggered by meaningful events.

Examples:

* A file changes.
* A new Thread Reference is added.
* A Decision is established.
* A Flag is raised.
* A Task is completed.
* An External Cutoff approaches.
* A Project hasn't been updated for a while.
* A new project is created.

For example:

```text id="6m3q8p"
EVENT

Task completed
        ↓
AUTOMATION
Ask AI to update
"Where Things Stand"
        ↓
AI UPDATE
Proposed / Authorized
```

### 2. Automation should not automatically imply authority

This is critical.

A trigger can say:

> "When Task X is completed, ask Claude to update Where Things Stand."

It should **not** implicitly grant Claude permission to change everything else.

The automation inherits—or explicitly declares—the Agent's permitted capabilities.

### 3. Automations should be visible

Eventually a project might have:

```text id="8q4m2v"
AUTOMATIONS

✓ On Task completion
  → Update Project State

✓ On new Flag
  → Notify AI Reviewer

✓ 14 days before External Cutoff
  → Generate attention report

○ On repository change
  → Run Project Review
```

That makes automation understandable rather than mysterious.

### 4. Automation should have conditions

For example:

> 14 days before cutoff

is different from:

> Every day.

And:

> If no Blocker exists

is different from:

> Always.

So eventually:

```text id="p7n3k8"
TRIGGER

When:
External Cutoff is 14 days away

Condition:
Project Status = Current

Action:
Generate AI attention report

Actor:
Project Review Agent
```

### 5. Some automations should be informational only

For example:

> "Project hasn't been updated for 14 days."

CC could simply surface:

> ⚠ **Stale Project**

without automatically changing its Status.

Again: **observation ≠ governance**.

### 6. Automation needs a safety boundary

Given everything we've established, I think there should be a simple principle:

> **Automation may perform only actions that its configured actor is authorized to perform.**

So:

```text id="w5q2m9"
Trigger
   ↓
Automation
   ↓
Actor / Agent
   ↓
Permission Check
   ↓
Allowed Action
```

No permission → no action.

### 7. Automation should be auditable

If an automation updates something, History should show:

```text id="k8m4p2"
AUTOMATED ACTION

Trigger:
External Cutoff approaching

Agent:
Project Review Agent

Action:
Created Attention Report

Time:
...

Result:
2 unresolved Flags identified
```

That keeps automation from becoming invisible system behavior.

### Matrix additions

| ID      | Requirement                                                                                                     | Status                                    |
| ------- | --------------------------------------------------------------------------------------------------------------- | ----------------------------------------- |
| P4-R551 | CC should support event-driven Automation and Triggers.                                                         | **Established architectural direction**   |
| P4-R552 | Automations should be able to respond to meaningful project events.                                             | **Established direction**                 |
| P4-R553 | Automation must not grant authority beyond the configured AI/Agent permissions.                                 | **Established architectural requirement** |
| P4-R554 | Automations should support conditions in addition to triggers.                                                  | **Established direction**                 |
| P4-R555 | Automations should be visible and inspectable by the user.                                                      | **Established direction**                 |
| P4-R556 | Informational automations should be able to surface conditions without automatically changing governance state. | **Established**                           |
| P4-R557 | Automated actions should identify their triggering event and executing AI/Agent.                                | **Established direction**                 |
| P4-R558 | Automated actions should be recorded in Project History where consequential.                                    | **Established**                           |
| P4-R559 | Automation should fail honestly when its required permission, source, or dependency is unavailable.             | **Established architectural principle**   |

### Category 40 verdict

This gives us the beginnings of a safe automation model:

**Event → Trigger → Condition → Authorized Actor → Action → History**

And importantly, we're **not designing an autonomous AI system**.

We're designing a system where you can progressively decide:

> "This is something I'd like CC/AI to handle automatically."

That's a much safer path.

## Step 4AX — Category 41: Notifications & Signals

This is related to Attention, but it's not the same thing.

**Attention** is what CC shows you when you're looking at a project.

**Notification** is CC telling you:

> **"You should probably look at this now."**

### 1. Not everything deserves a notification

This is important.

If CC notifies you every time:

* a Task changes;
* an AI writes a note;
* a file changes;
* a Flag is created;

you'll quickly stop paying attention.

So notifications need a **significance threshold**.

### 2. Signals can exist without notifications

For example:

```text id="6q4m8v"
SIGNAL

External cutoff:
18 days away

Project:
Conference

Current state:
3 required items incomplete
```

That can appear in **Attention** without necessarily generating a notification.

Then a rule might say:

> Notify Kurt when the cutoff reaches 7 days **and** required items remain incomplete.

That's much more useful.

### 3. Notification severity

I think three levels are enough initially:

**Info**

> Something happened.

**Attention**

> Something deserves a look.

**Urgent**

> Something may require immediate action.

For example:

```text id="8p3n7q"
INFO
Claude updated project notes.

ATTENTION
A Flag has remained unresolved for 10 days.

URGENT
External cutoff in 3 days and required submission is incomplete.
```

### 4. Notifications should point somewhere

A notification should never be a dead-end message.

Clicking it should take you to the relevant object:

```text id="m7q2v4"
⚠ External cutoff approaching

→ Open Project
→ Open Attention
→ Open related Tasks
```

Or:

```text id="r4n8k2"
⚑ New Flag raised

→ Open Flag
→ Open source Thread
→ Open related Decision
```

### 5. AI can recommend notification rules

An AI might notice:

> "You consistently react to External Cutoff warnings but ignore routine Task notifications."

It could suggest changing the notification policy.

But again, it shouldn't silently change your preferences.

### 6. Notifications should work across projects

The Command Center's top-level view could eventually have:

```text id="q5m8v2"
ATTENTION

3 projects need attention

⚠ Conference — cutoff approaching
⚑ Command Center — architectural Flag
⚠ TeacherToolbox — stale for 14 days
```

That fits your original goal of **seeing first, reading second**.

### 7. Notifications need persistence rules

Some notifications should disappear after you've acknowledged them.

Others should remain until the underlying issue is resolved.

For example:

> "New AI note" → dismissible.

> "External cutoff in 3 days" → remains active.

That's another distinction between the **notification** and the **underlying artifact**.

### Matrix additions

| ID      | Requirement                                                                                | Status                                  |
| ------- | ------------------------------------------------------------------------------------------ | --------------------------------------- |
| P4-R560 | CC should distinguish Notifications from the persistent Attention state.                   | **Established**                         |
| P4-R561 | Not every project event should generate a Notification.                                    | **Established architectural principle** |
| P4-R562 | Signals may be surfaced in Attention without generating a Notification.                    | **Established direction**               |
| P4-R563 | Notifications should support significance levels such as Info, Attention, and Urgent.      | **Established direction**               |
| P4-R564 | Notifications should link directly to their underlying Project or artifact.                | **Established**                         |
| P4-R565 | Notification rules should be configurable.                                                 | **Established direction**               |
| P4-R566 | AI may recommend notification-policy changes but must not silently alter them.             | **Established**                         |
| P4-R567 | Notifications should support different persistence/acknowledgement behaviors.              | **Established direction**               |
| P4-R568 | The top-level CC should be capable of surfacing significant notifications across Projects. | **Established direction**               |

### Category 41 verdict

The distinction is:

**Signal**
→ *Something happened or something may matter.*

**Attention**
→ *Something currently deserves visibility.*

**Notification**
→ *CC actively tells Kurt about it.*

**Urgent Notification**
→ *CC believes delaying attention could matter.*

That keeps the system useful without turning it into a notification machine.

## Step 4AY — Category 42: Search & Discovery

We've already touched Search several times, but now we can formalize what it needs to become.

The basic idea is:

> **Search should find things by what they are, where they are, and how they relate to the project.**

Not just filenames.

### 1. Search should be global

From the CC level, a search for:

> `WP13`

could potentially find:

```text id="6m8q2v"
PROJECTS
Command Center

FILES
WP13_Phase_3_Spec.md

REPOSITORIES
Command_Center

THREADS
GPT — WP13 Verification
Claude — WP13 Implementation

DECISIONS
D-071 — WP13 state injection

FLAGS
F-014 — onStateChange concern

HANDOVERS
GPT-5.5 → GPT-5.6

TASKS
Verify WP13 Phase 3
```

That's the sort of search that matches your actual workflow.

### 2. Search should understand location

You specifically raised the possibility of a file being somewhere it shouldn't be.

So Search should expose:

```text id="8q3n7m"
WP13-review.md

Found:
Downloads/

Associated Project:
Command Center

Registered Project Location:
Desktop/Projects_Folder/Command_Center

Status:
⚠ Outside registered location
```

That doesn't mean CC automatically moves it.

It means **CC found it**.

### 3. Search should understand relationships

Searching:

> `onStateChange`

might find a file that doesn't contain that exact filename but is connected through:

**File → Thread → Decision → Project**

That's much more valuable than ordinary filename search.

### 4. Search should be filterable

Eventually:

```text id="p7m4q2"
SEARCH

[ Everything ]

Type:
[ Files ] [ Projects ] [ Threads ]
[ Decisions ] [ Tasks ] [ Flags ]
[ Repositories ] [ Sources ]

Location:
[ Local ] [ iCloud ] [ Google Drive ]
[ GitHub ] [ External ]

Project:
[ Command Center ]

AI:
[ GPT ] [ Claude ] [ Qwen ]
```

But the default search should remain **simple**.

You shouldn't have to configure ten filters just to find a file.

### 5. Search results need context

Instead of:

> `orientation-bar.ts`

CC should show enough information to make the result meaningful:

```text id="r5n8k3"
orientation-bar.ts

Project:
Command Center

Location:
Command Center/src/...

Repository:
22cryys56p-beep/Command_Center

Related:
GPT — WP13 Verification
D-071 — Injection Pattern

[Open]
```

### 6. Search should support "where did this come from?"

This is especially important for Seeds and Handovers.

If you find:

> `WorksheetRenderer`

CC should eventually be able to tell you:

> Originated in TeacherToolbox Prototype → Seed → iCanSpell.

That's **discovery through lineage**.

### 7. Search shouldn't pretend to have access it doesn't have

This follows our Honest Failure principle.

If Google Drive isn't connected:

> **Google Drive — unavailable**

not:

> **No matching files found.**

Likewise, if an AI provider doesn't expose historical thread access, CC can search its **stored Thread References and metadata**, but shouldn't pretend it searched the provider's entire history.

## Step 4AZ — Category 43: The Project Dashboard

This is where all the architecture we've been defining finally comes together into the thing you actually **look at**.

The Dashboard should answer, at a glance:

> **What is this project? Where is it? What's happening? What needs attention? What do I do next?**

And it should follow the principle we've already established:

> **See first. Read second.**

### 1. The Dashboard should not be a giant information dump

The important information gets surfaced first.

Something along these lines:

```text

Status: Current

...

Focus

⚠ External Cutoff — if applicable
⛔ 0 Blockers

GitHub
Local

...

GPT-5.6
Claude
Qwen

THREADS
[Relevant Threads]

DECISIONS
[Recent / Important Decisions]

TASKS
[Immediate Tasks]

HISTORY
[Recent Events]
```

The exact visual arrangement is still a UI-design question. The **information hierarchy** is the important part right now.

### 2. Purpose, Description, and Focus stay separate

You established this earlier, and it belongs here.

**Purpose**

> Why does this project exist?

**Description**

> What is it?

**Focus**

> What are we working on right now?

They shouldn't be collapsed into one generic "Project Description."

### 3. "Where Things Stand" is the operational center

And as you specifically corrected earlier:

> **Attention is part of that whole section, not a subsection.**

So I would treat the Dashboard's operational area as one unified block:

```text
WHERE THINGS STAND

Current:
...

Attention:
⚑ ...

Next:
...

Recent:
...
```

The visual treatment can make these distinct without making Attention a subordinate section.

### 4. Dashboard information should be linked, not duplicated

If it says:

> ⚑ State injection concern

that's a link to the actual Flag.

If it says:

> D-071 — Injection Pattern

that's the actual Decision Record.

If it says:

> Claude — WP13 Review

that's the actual Thread Reference.

The Dashboard is a **view into the underlying CC data**, not another copy of it.

That is critical for maintaining the Single Source of Truth principle.

### 5. The Dashboard should adapt to the project

A software project might show:

```text
Repository
AI Threads
Build State
Implementation Tasks
Architecture Decisions
```

A conference project might show:

```text
Venue
Dates
Participants
Budget
Registration
Schedule
External Cutoffs
```

A construction project might show:

```text
Site
Contractor
Permits
Budget
Milestones
Documents
External Cutoffs
```

The underlying Project model remains common.

The Dashboard can expose the fields that actually matter.

### 6. Empty information should not create visual clutter

A project with no Blockers shouldn't display:

> Blockers: None

in giant text.

Likewise, a project with no External Cutoff shouldn't have an empty Deadline panel.

The Dashboard should **surface relevant information**, not display every possible field.

### 7. Dashboard should support AI-maintained information

This is where our earlier AI discussion becomes concrete.

AI could maintain:

* Where Things Stand
* Recent Activity
* Task state
* AI Thread references
* Review observations
* attention signals

while Kurt retains control over:

* Project Status
* authoritative Decisions
* governance
* major structural changes

So the Dashboard becomes a place where **AI-maintained operational information and Kurt-controlled governance information coexist visibly**.
